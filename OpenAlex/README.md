## The queries in use now (exported 2026-11-05, registered 2026-11-06)

The two queries above are **superseded** for percentile work. The RFE asked for a comparison
close to the exact field rather than a broad one, and the 2020 start date left 43.6% of the
packet's independent citations unrankable because their papers predate 2020. These two replace
it — one cohort per research programme, both reaching back to 2008:

```
get articles since 2008 in the topic [Glycosylation and Glycoproteins Research](T10602), most cited first
```

expected **25,326** works → `OpenAlex/T10602-glycosylation-2008.csv`

```
get articles since 2008 in the topic [Blood Coagulation and Thrombosis Mechanisms](T10881), most cited first
```

expected **26,517** works → `OpenAlex/T10881-anticoagulation-2008.csv`

Both downloads were verified against the API rather than accepted: parsing each file as RFC 4180
gives **25,326** and **26,517** records, matching `meta.count` exactly, with every year from 2008
to 2026 present and no gaps. The glycoscience cohort holds 1,035–1,584 articles in every year and
the anticoagulation cohort 876–2,594, so same-year matching is well-populated throughout.

Three things about the wording matter, each reproduced against the API rather than assumed:

- **`get articles` is not `get works`.** `articles` compiles to `type:article`; `works` is
  unfiltered. The original second query used `get works`, which is why it returned 15,371 rather
  than the 21,076 the same topic returns for articles. The two new queries use `articles`.
- **`in the topic [Name](ID)` compiles to `primary_topic.id`**, not `topics.id`. Filtering
  `topics.id:T10602` over the same window returns 35,263 and looks like a mismatch when it is not.
- **The bracketed name is cosmetic** — only the ID is read, so a wrong ID silently returns a
  different cohort. Check any new query's count before exporting it.

**Effect on coverage.** The share of the packet's 1,078 independent citations that can be ranked
against a cohort measuring its own programme and holding its own year went from **36.2% (390)** to
**98.0% (1,056)**. The residual **22** belong to 3 papers whose topic is neither programme
(a hemoglobin work, a porphyrin work, and a hemoglobinopathy work); no cohort measures their
field, which is the honest answer rather than a gap to fill with a broad cohort. The reasons are
published in the artifact as `coverage.unrankable_by_cause`, row by row.

**The `FWCI` column.** The export tool can append a sixth column, `FWCI` — field-weighted
citation impact, citations received divided by citations expected for that publication year,
field and author position. It is present on both new files for **every** row (25,315 and 26,510
usable records). It is worth keeping, and the workpaper now uses it as a second axis: each paper's
FWCI is ranked against its own cohort's **same-year FWCI distribution**, which is normalised for
age and field at once, so a 2011 paper and a 2025 paper are comparable on that axis without any
year matching. Cohort FWCI medians are 0.47 (glycoscience) and 0.00 (anticoagulation) with p90 at
2.49 and 2.21 — a reminder that the anticoagulation cohort's raw citation distribution is much
lower, which is exactly why ranking anticoagulation work inside it is the conservative choice.
Five-column files still parse; the header check accepts `FWCI` as an optional trailing column.

### Retirement of the broad keyword cohort (2026-11-06)

`works-2026-11-05T15-49-23.csv` (24,585 works, `get articles since 2020 with (glycan OR
glycosylation) in the title or abstract`) was deleted with `git rm` and its entry taken out of
`cohort-manifest.json`. It carried `exact: false`, so it fed **no** percentile, no coverage figure
and no chart — it existed only as a contrast, and the RFE asks for the opposite of a broad cohort.
It was also the odd one out in shape: the only export without the `FWCI` column, which meant every
FWCI code path needed a "cohort has no FWCI" branch to serve a file that produced no numbers.

What it was worth, measured before deletion so the argument survives it: it held **3.6% of its rows
on pandemic-related work carrying 13.5% of its citations**, and removing those rows moved its own
p99 from **103 to 92** citations. That is the pandemic effect the two exact cohorts do *not* show —
inside them the same rows are 139 of 25,315 and 84 of 26,510 — **0.5% and 0.3% of rows**, carrying
**1% and 0.3% of citations**. That measurement is why the pandemic exclusion itself was retired the
same day, at the user's instruction — see "The pandemic exclusion is not applied" below.

To bring a keyword cohort back, add an entry with `exact: false` and re-run the builder; nothing in
the tool needs editing.

### The pandemic exclusion is not applied (2026-11-06)

An earlier build carried **every cohort distribution twice** — whole, and with pandemic-related rows

## The field-comparison workpaper (built 2026-11-06)

`tools/build-field-comparison.js` reads three things and writes **nothing outside this folder**:

| | |
| --- | --- |
| **Reads** | `dashboard/data/citation-data.json` (read-only), the CSVs named in `cohort-manifest.json`, `OpenAlex/journal-abbreviations.json` for the venue abbreviations, and `GET /works?filter=author.id:A5083766160` for FWCI and the OpenAlex year |
| **Writes** | `OpenAlex/field-comparison.json` and `OpenAlex/field-comparison.js` (same payload as a `window.FIELD_COMPARISON` assignment, so the page opens over `file://`), plus `OpenAlex/journal-abbreviations.json` **only** when `--fetch-abbrevs` is passed |
| **Renders** | `OpenAlex/field-comparison.html`, opened directly in a browser. It borrows `../dashboard/styles.css` and `../dashboard/vendor/d3.min.js` but is **not** wired into the dashboard's contents bar |

```
node tools/build-field-comparison.js
node tools/build-field-comparison.js --fetch-abbrevs   # refresh the NLM abbreviation cache from PubMed
```

The abbreviation cache is read on every build and contacted against PubMed only under the flag, so a
normal rebuild makes no network call to NCBI. `tools/env.js` loads `NCBI_API_KEY` / `CROSSCHECK_EMAIL`
from `.env` at require time; the look-up works anonymously at the slower rate, and no credential value
is ever logged or placed in a URL.

**Why it is not a dashboard chapter.** The packet is Google Scholar based and frozen; everything
here is OpenAlex. Keeping the pages apart is what stops a field percentile being read as a packet
figure, and adding a chapter would renumber every later page (the number lives in four places).
Revisit only once the design is agreed.

**Adding an export is a manifest edit, not a code change.** Append an entry to
`cohort-manifest.json` with `id`, `label`, `file`, `oql`, `field` (`glyco`, `anti`, `both`) and
`exact`, drop the CSV in this folder, re-run the builder. A cohort is only used for a paper whose
own programme it measures — anticoagulation papers never rank against a glycoscience cohort — and
each cohort publishes one distribution, whole.

### Notes for anyone changing the tool

- **Match on a prefix only when it is long and unique.** `buildTitleMatcher` requires at least
  8 leading normalised words *and* exactly one OpenAlex work satisfying them. A two-word prefix
  matches unrelated papers; a shared prefix settles nothing. When either test fails the row stays
  unmatched — the same floor `tools/crosscheck.js` uses for the same reason.
- **Percentiles are taken inside the paper's own OpenAlex publication year.** The glycoscience
  cohort's median falls from **11** citations for 2008 papers to **0** for 2026 papers, and the
  anticoagulation cohort from **2** to **0**, so a pooled ranking rewards age rather than impact.
  The OpenAlex year governs both sides; where Scholar disagrees (5 rows) the row says so.
- **`ordinal()` rounds before choosing the suffix.** A percentile of 92.9 prints as 93 and must be
  93**rd**. Reading the suffix off the unrounded value produced "92th" across the page.
- **The pandemic toggle is gone, and so is the `mode` variable it drove.** Removing a control that
  threaded through the page means checking every consumer, not just the buttons: `bestRank()`,
  `ladderRows()`, `drawFwciPct()`, the three ladder captions, the FWCI-ladder caption, the cohorts
  table's last two columns and its caption, one methods step, one "not done" item, `rankShift()`, the
  `.controls` CSS and its print rule, and the `#controls-pct` div. The failure mode if one is missed is
  a `mode is not defined` throw that kills the IIFE and blanks every chart and table at once. Assert
  `pageerror` is empty, then assert `document.querySelectorAll("button").length === 0`.
- **The percentile section is three charts, one per programme** — glycoscience, anticoagulation,
  and the dual-programme papers drawn once inside *each* cohort. A single merged ladder would put a
  99th percentile in the thrombosis literature on the same axis as a 99th percentile in the
  glycoscience literature as though the two distributions were one, which is the comparison the
  RFE objects to. Bars are coloured by the **cohort** a row was ranked in, never by the paper's own
  programme label, because on the dual-programme chart one paper appears twice. Its caption therefore
  states each cohort's distribution as a separate sentence naming the cohort ("In the Anticoagulation
  cohort, p50 / p90 …"), which first read as two identical sentences when both were worded the same.
- **Ladder titles print in full, wrapped over up to four lines**, at the user's instruction — a
  truncated title is not enough to tell one paper from the next. `wrapToWidth` measures in the real
  rendered font via `getComputedTextLength`; a character budget is wrong by enough to clip on titles
  dense with enzyme and gene names. The label column is sized to the widest line that actually came
  out, each row is as tall as its own label, and the bar keeps one thickness centred in it — a bar
  that grew with its label would read as a second, meaningless quantity. All rankable rows are now
  drawn (24 / 10 / 6), so the old 14-row cap is gone.
- **`getComputedTextLength()` on a multi-`tspan` `<text>` element is not the width of its widest
  line** — for right-aligned lines it includes the backwards jump between them, roughly doubling the
  figure. Measure each `tspan` separately when checking whether a wrapped label fits its column.
- **The FWCI chart draws the top 15 only.** The percentile ladders draw every rankable row because
  each answers a different question, but this chart orders one quantity end to end, so its head is
  the point and its tail is a flat run near the expectation line. The caption names how many were
  left out and where to find them (the publication table further down carries all 45), and the legend
  counts follow the **drawn** rows — a key reading "Glycoscience (24)" above a chart holding eight
  would look like missing bars.
- **The FWCI percentile ladder deliberately mixes the two literatures.** `#chart-fwci-pct` draws one
  axis holding both programmes, which is the opposite of the rule for the CITATION ladders. It is
  defensible because each bar is already a percentile taken inside the paper's own cohort and its own
  publication year, so the axis is a position within the paper's own literature, not a count the two
  literatures would share; the bar is coloured by the cohort it was ranked in and the caption names
  both. A raw-count ladder has no such excuse — there, 99th percentile in thrombosis and 99th in
  glycoscience would be plotted as though the distributions were one.
- **Ladder bar-labels sit above the bar, not inside it or beside it.** At the user's instruction the
  `n=… · percentile` annotation moved to a lane reserved above each bar (`ABOVE` in the row-height
  arithmetic) with no white halo. The class is `.bar-label--over`, scoped so the programme and
  age-distribution charts keep the haloed `.bar-label` they need for text drawn on a filled bar. A
  label to the *side* of a bar would extend the plot's effective width and read as part of the axis.
- **Journal abbreviations are NLM/PubMed-compliant, not invented.** `OpenAlex/journal-abbreviations.json`
  is built by `node tools/build-field-comparison.js --fetch-abbrevs`, which resolves each venue through
  the DOI: `esearch.fcgi` with `db=pubmed&term="<doi>"[doi]`, then `esummary.fcgi`, whose `source` field
  *is* the MEDLINE abbreviation and `fulljournalname` the official title. Credentials go in the POST
  body, never the URL — a failed request is recorded as `${msg} :: ${url}` and that note can ship in a
  report JSON. Three rules make the look-up safe, and each exists because it failed without them:
  - **OpenAlex writes DOIs as resolver URLs** (`https://doi.org/10.1002/…`) while PubMed's `[doi]`
    field holds the bare name. Every search returned nothing until the prefix was stripped.
  - **Never search a nullish value.** Three patents have no DOI, and `"null"[doi]` returned a real
    unrelated PubMed record (`Curr Drug Saf`) that would have labelled all three with a journal
    abbreviation. No DOI means no look-up: the row is recorded `lookup: "none"` and prints Scholar's
    own venue text.
  - **`sameJournal()` admits the registry's longer official title only on a floor.** Scholar prints
    `Journal of Biological Chemistry` where NLM holds `The journal of biological chemistry`, and
    `Proceedings of the National Academy of Sciences` where NLM holds `…of the United States of America`.
    A leading "The" and a dropped tail beginning with a connector are allowed, but only when the short
    side is **three words or more** — otherwise `Science` would match `Science Advances`.
  Result: **43 of 48 rows** carry an abbreviation. The five that do not are correct refusals — three
  patents, the VCU dissertation, and a book chapter where Scholar printed the *book's* title while the
  registry holds the series (`Methods Mol Biol`). A venue that cannot be abbreviated is printed exactly
  as Scholar wrote it; it is never guessed at.
- **Scholar's venue string is parsed right-to-left on `", "` because a patent's commas have no space.**
  Scholar appends ` volume (issue), pages , year` to the journal name, and `venueName()` strips the
  trailing year, then the page range or article number, then ` (12)`, then the volume. The separator is a
  comma **followed by a space**; `US Patent 20,160,115,280` uses commas with no space, so the same regex
  that finds the page separator leaves a patent number intact. The first attempt required whitespace
  before the comma in a different position and ate too much of the volume, and left all 48 venues
  distinct instead of collapsing them to **37 venues / 35 lookup keys** — which is what makes one
  PubMed look-up per journal rather than per paper.
- **Anything appended after wrapping must be reserved in the wrap budget.** The FWCI rows print the
  publication year after the title, and adding it *after* the wrap pushed the last line past the
  column that had been sized for the title alone. `measureTextWidths([" (2019)"], cls)` is subtracted
  from the budget before wrapping and added back to the column width.
- **A `const` declared below the call that uses it is in its temporal dead zone when that call
  runs.** `const FWCI_TOP = 15` sitting between `drawFwci()` and the function body threw
  `Cannot access 'FWCI_TOP' before initialization` and killed the entire inline script — the same
  failure mode as a duplicate `const`, and the symptom is again every SVG rendering as missing, not
  an error at the declaration site.
- **The table prints the more modest percentile for a dual-programme paper.** Such a paper has a
  legitimate ranking in both cohorts; the table takes the lower and names the cohort in the "Ranked
  in" column, while the dual-programme chart shows both. Defaulting to the first cohort listed would
  have quietly picked whichever export happened to be registered first.
- **Every unrankable citation is named, not summarised.** Coverage is not printed as a bare "98.0%":
  a table under "Every publication" lists each paper that cannot be ranked, its year, its independent
  citations, its primary topic and the cause, with the causes coming from
  `coverage.unrankable_by_cause` in the JSON. A percentage alone would let a reader assume the missing
  2% was random; in fact all 22 sit on 3 papers whose primary topics (T12094, T12441, T10554) fall
  outside both programmes, which is a specific reason with a specific non-fix. If a future cause
  appears — a cohort that stops holding a year, say — it becomes a row here automatically. The cause
  code from the JSON ends in the paper's programme key, so the page rewrites it in the reader's own
  vocabulary (`(other)` prints as `(Neither programme)`) and keeps the raw code in a tooltip.
- **The two wide tables scroll inside their own container.** `tbl-papers` (10 columns) and
  `tbl-cohorts` (13) cannot shrink to a narrow window, and without `overflow-x: auto` on the div
  around them the table widened the *document*: the whole page scrolled sideways and the masthead
  stopped spanning the sheet. Measured at 900 px the page had 246 px of sideways scroll; now it has 0
  and each table scrolls to its own last column. On paper that rule is switched back to `visible`
  (a scrollbar is a screen affordance) and the header cells are allowed to wrap over two lines with
  tighter padding — at Letter content width the publication table was 731 px against 701 px of sheet,
  and Chrome clips whatever hangs past the page edge and warns about nothing.
- **The publication table holds all 48 publications, not the 45 matched ones.** Its heading is
  "Every publication" and its lede promises the three Scholar titles OpenAlex does not hold, but the
  rows came from `papers` (the matched subset), so a reader could not find those three anywhere on the
  page. They now render with no id, no count and no percentile, in a faint `td.absent` — a distinct
  class from `td.inferred`, which already means "matched on a prefix", and the two states must not read
  alike. `PAPERS_DEFAULT` therefore sorts `D.articles`, not `papers`.
- **The Publication column never truncates, and it absorbed the Year column.** Each cell is the full
  title (wrapping, `white-space: normal`, no ellipsis) then the venue on its own line: the NLM
  abbreviation in italics and the year Google Scholar gives the paper in bold. A separate Year column
  was redundant once the year sat under the title, so `PAPER_COLS` is 10 entries and the print block's
  `table-layout: fixed` weights were re-cut for the narrower set. Two things follow. The `year_disagreement`
  tooltip that used to live on the Year cell moved onto the title cell — dropping it silently would have
  hidden the fact that five rows disagree with OpenAlex about their own year. And one title still shows
  an ellipsis because **Scholar itself truncates it** (`…Insights into NO-Releasing …`); that character
  is in the source record, not a `truncate()` call, and the helper was deleted rather than left to
  reappear. Never re-add truncation to that column.
- **Every column of that table sorts**, on click and on Enter/Space. Numeric columns open descending,
  text columns A→Z, a second click reverses and a third returns to the default (citations descending)
  so a reader who sorted by year can get the packet's own view back without reloading. A row with no
  value in the column is parked last **in both directions** — sorting a blank percentile as if it were
  a zero would put "no cohort holds this year" at the top of an ascending sort, where it reads as the
  worst paper rather than the unanswerable one. Ties fall back to the default order so a printed copy
  and a screen agree. `PAPER_COLS` carries a `val` (numeric, returns `null` rather than the printed
  string — "100th" sorts under "11th" as text) or a `text` accessor per column.
- **Memoise per row object, never per `openalex_id`, when a row may not have one.** `RANK_OF` and the
  tie-break index map are keyed by the row object itself. Keying them by `a.openalex_id` looked harmless
  and was not: the three unmatched publications have `openalex_id: null`, so a `Map` collapsed all three
  onto one key and handed each of them the same memoised rank and the same tie position. Object identity
  is the only key that is unique across a list that mixes matched and unmatched rows.
- **A `<th>` needs `tabindex="0"` before a `keydown` handler on it is reachable.** Adding Enter/Space
  sorting without it left the handler in the page but unreachable from the keyboard; the check is
  `th.focus()` then dispatch, then assert `document.activeElement` is still a header after the re-render
  (the header is rebuilt on every sort, so the code re-queries and refocuses it).
- **The page documents its own method**, at the user's instruction: a "How this analysis was performed"
  section at the foot, with an inputs table (each source, what it supplied, and what was taken from it —

### OQL syntax notes learned while validating

- Year upper bounds work only as `where year before YYYY`. `between X and Y`, `from X to Y`,
  `since X until Y`, `where year X-Y` and `where year is before Y` all fail.
- Keyword terms belong in the *works phrase*, not the `where` clause: `get works since 2011
  with glycomics in the title or abstract where type is article`, not `… where … glycomics …`.
- A bare `in topic T10602` fails; the bracketed `[Name](ID)` form is required.
- Adding a `where` clause to `get articles …` fails with `unknown entity type "articles"`; use
  `get works … where type is article`.
- `in the title` compiles to `display_name.search`, not a title-only field.
- Multi-word unquoted phrases such as `about glycan microarray` fail; quote them.
- **The bracketed topic name is cosmetic.** `[Glycosylation and Glycoproteins Research](T10602)`,
  `[Totally Wrong Name](T10602)` and `[](T10602)` all return the same 21,076 works. Only the ID
  is read, so a mistyped name cannot break a query — but a wrong ID silently returns a different
  cohort, and nothing in the response says so. Check the ID against the count table above.
- `since YYYY` is **inclusive** of that year: `since 2011 … year before 2027` returns works whose
  earliest publication year is 2011, and `since 2010` gives 22,450 against 21,076 for 2011 and
  19,682 for 2012. So the two bounds describe a closed 2011–2026 window.
- `and year before 2027` is **currently a no-op** — T10602 articles return 21,076 with the bound,
  with `year before 2028`, and with no upper bound at all, because the cohort contains no works
  dated 2027 or later today. It is kept in the queries above as insurance so the counts stay
  reproducible if OpenAlex later ingests forward-dated records; removing it changes nothing now.

### Practical constraint on the exports

The CSV columns are `Title, Author, Year, Citation count, Open access` plus an optional trailing
`FWCI` — there is **no DOI, no OpenAlex work id, and no topic column**. So the cohort a row belongs
to is carried by the *file*, not the row: export each query to its own named file and do not
concatenate them.

Measured 2026-11-06 on the two cohorts in use, parsed as RFC 4180 (header excluded). File A is
`T10602-glycosylation-2008.csv`, file B is `T10881-anticoagulation-2008.csv`:

| | A (glyco) | B (anti) |
| --- | --- | --- |
| Parsed records | 25,326 | 26,517 |
| Records with a blank title | 11 | 7 |
| Usable rows (title present) | 25,315 | 26,510 |
| Titles repeating | 449 (1,313 rows) | 453 (2,673 rows) |
| Empty `Author` cells | 271 | 542 |
| `Author` cells containing a comma | 78 | 144 |
| Exactly-100-name author lists | 4 | 7 |
| Lists of 98 or 99 names | 0 | 0 |
| Newlines in file | 25,327 | 26,518 |
| Rows carrying an FWCI value | 25,326 (all) | 26,517 (all) |
| UTF-8 BOM | none | none |

- **Title is the only join key, and titles repeat** — 449 and 453 titles appear more than once,
  covering 1,313 and 2,673 rows. A title match is never a one-to-one join. The repeat counts above
  use full normalisation (lowercase, non-alphanumerics collapsed); a different normalisation gives
  a different number, so never quote one without naming it.
- **The `Author` column is `|`-separated, but commas occur inside the cell.** Splitting on `,`
  manufactures phantom authors.
- **A pipe-split list of exactly 100 names appears 4 times in A and 7 times in B, while 98 and 99
  appear zero times** — the list is capped at 100, so a 100-name list is truncated and must never
  be read as proof that nobody is on the paper. This is the same trap the citation-record rules
  refuse to fall into for Scholar's `and others`.
- **One newline per record** (25,327 and 26,518 including the header line), so no field contains a
  line break. RFC 4180 parsing is still required because of the quoted commas.
- Files are **UTF-8 without a BOM** and carry substantial non-ASCII text (255 KB and 557 KB). If
  CJK or Cyrillic prints as `?`, that is the console, not mojibake in the data.
